import type { AppDefinition } from "rendrix/types";

type CounterState = { count: number };

// Runs in QuickJS inside the native host process, not in a browser.
const app: AppDefinition<CounterState> = {
  state: { count: 0 },
  actions: {
    increment(api) {
      api.set("count", api.get("count") + 1);
    },
    decrement(api) {
      api.set("count", api.get("count") - 1);
    },
    reset(api) {
      api.set("count", 0);
    }
  }
};

export default app;

Interactive simulation of the counter's layout and colours. The real window is drawn by the Rendrix host from the compiled .rdx.

Three parts, one job each.

Markup is compiled ahead of time, logic runs in a small sandbox, and the pixels come from the Rendrix engine. Nothing in the shipped app asks for a browser or a JavaScript runtime.

Markup and styles

A strict subset of HTML and CSS is parsed at build time into an element tree with explicit keys. CSS selectors, specificity and inheritance are resolved before anything reaches the window, so the layout you write is the layout that ships.

TypeScript backend

One backend.ts exports state and actions. It is transpiled to JavaScript and run in embedded QuickJS on the UI thread. Actions are synchronous and see only get, set and update.

One executable

Packaging copies a prebuilt Rendrix host and appends the app bundle to it. The result is a single .exe that runs without Bun, Node or Rust on the machine.

From source files to one native executable.

Each stage writes a file you can inspect. The bundle is plain JSON, so you can open it and see exactly what the host will render.

rendrix build

Copies the prebuilt host and appends the bundle, then the host reads it back at startup.

host bundle len RENDRI01

Host executable, then the bundle JSON, an 8-byte little-endian length and the RENDRI01 marker.

→ dist/rendrix-counter.exe

A small, native backend.

The design trades browser breadth for a smaller, inspectable system. These are the properties the current prototype is built around.

  1. Parse

    Strict HTML subset to an element tree with explicit keys and attributes. Unsupported tags fail the build.

  2. Style

    CSS parsed with PostCSS. Descendant matching, class and id selectors, inheritance and specificity are resolved.

  3. Transpile

    The single backend file is compiled with the TypeScript compiler to CommonJS (ES2020).

  4. Render

    The Rendrix host opens a GPU-accelerated window and draws the tree. Media queries are evaluated at compile time.

  5. Run

    Clicks invoke actions in QuickJS. The view takes a state snapshot and redraws. QuickJS has an approximate heap cap, not a CPU-time limit.

One rendering engine

Rendrix is the only engine, in early beta; the deprecated legacy host stays available until the Rendrix M1 gate.

No Node or Bun at runtime

Bun or Node is needed for development. The distributed app does not need either one installed.

Fast iteration

Changing HTML, CSS or TypeScript recompiles the bundle and reuses the existing host. Rust is not rebuilt.

Plain-text bundle

The .rdx document is JSON. Its format and contents can be read and checked directly.

Compile-time components

<template data-component> is expanded at compile time. Recursive uses and duplicate IDs are rejected.

Explicit data binding

data-bind and {{stateKey}} read backend state. data-onclick dispatches named actions.

Build the counter from a checkout.

Requires Bun or Node 20+ for the developer CLI. Compiling the bundle does not need Rust. Building the native host does.

Check and compile the example

bun install
bun run test
bun run rendrix:compile

Writes examples/counter/dist/rendrix-counter.rdx.

Get a native host, once per machine

Either point RENDRIX_HOST at a host you trust, or compile one with the Rust toolchain. On Windows that also needs the MSVC build tools. 

bun run rendrix:host

Package the executable

bun run rendrix

Writes examples/counter/dist/rendrix-counter.exe.

Or install the CLI from npm

bun install -g @bytethedeveloper/rendrix
rendrix --version

-g installs rendrix globally. Without it, Bun adds the package to the current project's node_modules. npm works too: npm install -g @bytethedeveloper/rendrix. View the package on npm.

Or start a new project with the CLI

rendrix init my-app
cd my-app
rendrix dev

rendrix dev rebuilds and restarts the host on save. It is a fast reload, not state-preserving hot module replacement. rendrix build writes the single executable, and rendrix build --target linux-x64 or rendrix all packages the other platforms. rendrix run also opens an Electron project directory, converting it first.

Status: an experimental prototype, stated plainly.

Rendrix is not a production-ready GUI SDK. The Rendrix engine is the sole renderer and is in early beta: feature coverage is limited and a long way from stable. The list below reflects what the deprecated legacy host (available until the Rendrix M1 gate) documents today.

Works today

  • Strict HTML subset with class, id, data-bind and data-onclick
  • Forms, text inputs, textareas and keyboard editing
  • Images, repeated data lists and optional virtual scrolling
  • Media queries that update when the window is resized
  • CSS with element, class, id and compound selectors, specificity and inheritance
  • Flex and grid layout, including mixed px/fr tracks
  • Synchronous backend actions with get, set and update
  • Confirmation prompts, clipboard, file access and allowlisted network requests
  • Compile-time <template> components
  • Single-executable packaging with the appended bundle, plus an optional NSIS installer on Windows
  • Cross-target builds for Windows, macOS and Linux on x64 and arm64, using verified prebuilt hosts
  • Electron project conversion into a Rendrix project, with a report that lists what needs review

Not yet

  • Rendrix feature coverage: state-driven re-render, hover/active/focus, scrolling, images, text editing, accessibility and animations are on the M1–M3 ladder
  • General-purpose native dialogs beyond confirmation and file picker prompts
  • Unequal sizing for pure fr grid tracks and explicit grid placement
  • Sandbox isolation for untrusted backend code; execution time and heap limits are not a sandbox
  • Built-in signing or encryption: signing runs a command you configure, and packages are neither encrypted nor tamper-proof
  • Complete Electron compatibility: the importer lists each partial or unsupported API

Only run backend code and Electron projects you trust: execution limits are not a sandbox, and importing an Electron project runs its build script. The container format is a prototype. The Windows host has been run by hand. Hosts for other platforms are built in CI and have not been run here.
